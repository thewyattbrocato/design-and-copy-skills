Principles

Each one has a reason, so people can make good calls in cases we did not predict.

Calm inside

Owners often arrive worried. Forms and records use plain, predictable patterns; warmth shows up in color, wording, and spacing, not decoration.

Never color alone

Status always carries an icon or text as well as color, so it survives color-blindness, glare, and forced-colors mode.

Plain words

Say what happened and what to do next. “Your visit is booked” beats “Success!”.

Color: three tiers

Raw values feed semantic roles, and components only read roles. A theme is a different mapping of the same roles, so dark mode is never an inversion. Hex values are proposals; confirm contrast with your own tooling before launch.

1 · RawNeutral, teal, plus one hue per status. Named by hue and step, e.g. --raw-teal-600. Not used in components.
2 · Semantic roleNamed by job: --text-secondary, --surface-raised, --accent, --danger. This is what components use.
3 · Component (rare)Only when a component needs its own knob, kept private, like --_c in status-message and badge.

How this stays consistent

Light rules for a small team. This page and the CSS variables at the top are the single source: if a screen disagrees with them, the screen has a bug.

Building a screen

  1. Use an existing component. If none fits, compose from tokens.
  2. Never write a hex, pixel size, or duration in screen CSS; use a token.
  3. Need a one-off value? Keep it local and comment /* exception: reason */.
  4. New pattern needed by a second screen? Propose it for the system (below).

Changing the system

  1. Add: a pattern joins on its second real use, with all states documented.
  2. Modify: change the role’s value once, here, and check text pairs in both themes.
  3. Deprecate: mark it here with the replacement before removing.
  4. Remove: only after nothing uses it. Record every change in a changelog. Owner: [name].
