Calm, clear, and careful with the details.

One small set of decisions, made once, so booking, pet records and reminders look and behave the same no matter who builds the screen. Everything below this line is built from the tokens on this page.

How we build

Four principles, each with a reason. They decide the cases the tokens don't.

Warm in tone, plain in structure

Personality lives in color, the serif headings and the wording. Forms, tables and buttons stay conventional, because people booking care for a sick pet are not here to explore.

Never color alone

Status always pairs color with words or a symbol. Reminders get read on bright phones, by color-blind owners, and in print.

Roles, not values

Components use --color-text-secondary, never a hex or a ramp step. That is what lets dark mode and future brands work without touching components.

Easy to tap, easy to read

Targets are at least 44px, body text is 16px, and focus is always visible. Many of our users are on a phone in a waiting room.

Using and changing the system

Short on purpose. The system should make building faster, not add a process.

Rules for builders

  1. Use a role, not a value. If you type a hex or a pixel number, stop and pick a token.
  2. Need something that isn’t here? Use the nearest step. If it truly doesn’t fit, mark it as a local exception with a comment.
  3. Reuse a component before building one. A pattern joins the system when a second screen needs it.
  4. Ship every state: default, hover, focus, disabled, loading, error, and long or empty content.
  5. Check light, dark and keyboard-only before you ask for review.

Use and misuse

Do · color: var(--color-text-secondary)
Don’t · color: #4A585D or var(--raw-ink-700) in a component
Do · Name a pattern for what it is: appointment-card
Don’t · Name it for where it started: dashboard-teal-box

Changing a token or component

ChangeWhat it takes
AddA second real screen needs it. Say which, and which existing token it can’t cover.
ModifyShow the before and after in light and dark. Note every component that reads it.
DeprecateMark it, name the replacement, and write the migration before removal.
RemoveOnly after nothing uses it. Record it in the changelog.
